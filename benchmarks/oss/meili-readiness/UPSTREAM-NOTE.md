# Maintainer note on Meilisearch’s historical federated-filter regression

SPE reproduced a latency regression between v1.41.0 and v1.42.0 on an ordinary two-index catalog search. Current Meilisearch already has a broader implementation of shared filter text. PR #6509 changed ownership of parsed filters, and PR #6695 introduced shared original text and byte ranges. The latter is listed in v1.56.1. In v1.58.0, `FilterCondition::parse` creates one shared original and `OwnedSpan` stores a range into it. This note offers historical measurements and a replay fixture. A new implementation PR for current Meilisearch would duplicate upstream work. [Issue #6354](https://github.com/meilisearch/meilisearch/issues/6354) · [PR #6509](https://github.com/meilisearch/meilisearch/pull/6509) · [PR #6695](https://github.com/meilisearch/meilisearch/pull/6695) · [v1.56.1 release](https://github.com/meilisearch/meilisearch/releases/tag/v1.56.1) · [v1.58.0 parser](https://github.com/meilisearch/meilisearch/blob/36dabf361a17c223e91cadc8ecf0378e90affc4b/crates/filter-parser/src/lib.rs#L85)

**Historical patch.** During federated query partitioning, v1.42.0 converts a cloned filter into an owned representation. Our experiment changed only the parser’s ownership conversion for `IN` membership tokens. Values borrowed from the field’s original input share an immutable source context while preserving their own fragments, modified text and diagnostic context. Foreign and pre-owned contexts retain their existing behavior. The original test drops the borrowed inputs before checking those values. Upstream’s current range-based design also avoids storing a separate fragment for each token. [v1.42.0 call site](https://github.com/meilisearch/meilisearch/blob/02ff9a4a1cae79ce405638b6323fbd2f939f7f67/crates/meilisearch/src/search/federated/perform.rs#L1123) · [Tested historical patch](../meili-share-filter-context.patch)

**Evidence.** In twelve fresh, balanced process pairs per comparison, the median paired change in mean request latency was −42.1% on AMD EPYC and −27.9% on Intel Xeon with the same reduced-feature ELFs and corpus. With normal features and authentic language dictionaries, the Intel latency improvement was 28.5% (96.1% interval, 19.3–30.2% faster). Patched v1.42.0 still trailed v1.41.0 in the reduced builds on both machines. With normal features the estimate was +12.3% [+8.7%, +18.2%], crossing the prespecified +10% threshold. A separate eight-value parser conversion dropped from 18 allocation requests and 624 requested bytes to 11 and 184. Empty and singleton lists requested 32 and 18 extra bytes respectively. These counts cover the conversion only. End-to-end empty and singleton list timings had wide intervals, leaving their HTTP effect unresolved. The full study includes normal-feature builds, error responses, indexing and process memory. [Results and limitations](README.md)

**Residual.** The version pair changes both federated filter preparation and the locked storage dependencies. The application’s nested stage timers and sampled CPU constrain the investigation but do not isolate an LMDB or parser function as the cause of the entire gap. The measured latency percentages apply to the two historical releases and intervention. No current-release performance claim follows from the source comparison.
